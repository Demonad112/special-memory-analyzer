# Security notes: threat model for release, USB kit and app

**Scope:** how the app gets from the repo onto a server, plus the elevated-app attack surface. Finding IDs refer to `02-FINDINGS-REGISTER.md`.

## Assets

1. The **target server's trust store**: the kit adds a certificate to `LocalMachine\Root` and `TrustedPublisher`.
2. **SYSTEM execution** through the `DSA-TrustExpiry` scheduled task.
3. **Client data on disk**: the files Disk Cleanup can delete, and Record reports used as proof of a migration.
4. The **integrity of reports**: copied, missing and deleted lists.

## Actors

| Actor                          | Capability                                                                                              | Realistic?                                                      |
| ------------------------------ | ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| A1: network or mirror attacker | Swaps the zip between GitHub and the admin (proxy, shared drive, USB in transit, a "helpful" re-upload) | Yes. USB kits pass through hands                                |
| A2: repo-write attacker        | Pushes a `v*` tag or edits workflows                                                                    | Low (owner-only repo today), but it bypasses every in-kit check |
| A3: local standard user        | Writes to `%LOCALAPPDATA%` (their own), can create folders in `C:\ProgramData`                          | Yes on shared servers                                           |
| A4: content in the webview     | Script injection through a rendered file name or report field                                           | Low (no `v-html`, Vue escapes), but no CSP backstop             |

## What is already done well (keep it)

- **Signing key hygiene.** The key is ephemeral: generated per release, used once, and deleted in an `if: always()` step. No signing secret lives in the repo or in GitHub secrets.
- **CI verifies the installer's signature.** It checks the signer thumbprint and requires a timestamp before publishing.
- **Workflows.** Every action is pinned by SHA. Default `contents: read`; write only in the release job.
- **Kit behaviour.** The kit refuses to run the installer unless its Authenticode signer equals the trusted certificate. Trust is time-boxed, with a removal task that also fires at startup. On any install failure, the kit removes the trust in `catch`.
- **App export safety.** HTML export escapes everything, embeds JSON safely, and uses a hash-based CSP. CSV export defuses formulas.
- **Delete safety.** Deletes go to the Recycle Bin by default. Admin is required for permanent or big runs, which use a confirm token. Every bulk delete is logged.

## Residual risk after B02–B05

The kit still asks admins to add a root certificate, even if only a constrained, short-lived code-signing one. Root stores trust certificates for every purpose the certificate allows, and Windows honours EKU constraints. With the constraint checks, a compromised kit is limited to code signing, plus whatever the installer itself does as admin. **Recommendation (DSA-066):** move to a publicly trusted signing identity, for example Azure Trusted Signing, and retire the root-store step for internet-connected machines.

## Not assessed

- **GitHub repo settings:** branch protection, tag rules, who has write access.
- **The NSIS installer's own behaviour:** Tauri's template was not reviewed.
- **WebView2 bootstrapper download integrity:** Microsoft-signed, so out of scope.
- **Runtime behaviour on a live server:** nothing was executed against real data, by the rules of this review.
