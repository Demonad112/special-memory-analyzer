# 1.3 implementation plan

Ten batches, each sized for one session. Feature details (behaviour, risks, acceptance) are in [`1.3.md`](1.3.md). This file says **what order**, **which files**, and **how to prove it worked**. Session prompts are in [`prompts/`](prompts/).

## Ground rules for every batch

- **Merge hold:** nothing merges before the owner has tagged v1.2.0 (see `1.3.md`). Sessions may open PRs earlier.
- Branch per batch from up-to-date `main`: `feat/r<NN>-<slug>` (R10: `chore/r10-release-1-3`). One PR per batch.
- One commit per feature step, subject `F-0NN: <imperative summary>` (R01: `R01: <summary>`; R10: `chore: ...`). Message ends with the `Co-Authored-By` line; use `git commit -F <file>`.
- Tests with every behaviour change, written first where practical. Pure logic (name rules, ACE decoding, diffing, grouping, forecasting) is split from the Windows calls so it is tested on every platform.
- After a feature is done, append **Done in `<short-sha>` (R0N).** to its Status cell in `1.3.md` and run Prettier on that file.
- Full gate before the PR is marked ready: `corepack pnpm check`. Windows-only code (`#[cfg(windows)]`) is compiled and tested only by the Windows CI job ("Quality and tests" runs on `windows-latest`); cloud sessions say so in the PR.
- Saved formats change additively only: new fields `#[serde(default)]`, new report kinds as new `Body` variants, nothing renamed or removed.
- Every delete goes through `cleanup_core::bulk::run` with a `deletions.jsonl` line. Folder walks never follow reparse points. OneDrive online-only files are never opened, read or hashed.
- Long jobs: `async` command + `spawn_blocking`, progress about every 100 ms, results in managed state, the UI loads one folder level at a time. Every `await` that writes shared state checks a sequence or owner token.
- Every colour is an `--app-*` token in `src/styles.css`.
- No new crates. Features of crates already in `Cargo.lock` are allowed where `1.3.md` D-13 and D-24 list them; the PR names each one. Run `cargo deny --manifest-path src-tauri/Cargo.toml check advisories licenses bans` if a `Cargo.toml` changed.
- Apache-2.0 only: never copy source from GPL tools (WinDirStat and others). Microsoft docs and MIT/Apache crates are fine as references.
- DRAFT PR first, `gh pr ready` when CI is green and the "Not done yet" list is empty. Never merge, tag, release or force-push.
- New problems found along the way are logged in the PR body under "Found along the way", not fixed in the batch.
- Rollback for every batch: revert the PR's merge commit (`git revert -m 1 <merge>`). Saved files written by the new version stay readable by the reverted build because every change is additive.

"Parallel" means the batches touch disjoint files, apart from three shared one-line lists that conflict trivially and are resolved by keeping both sides: the `generate_handler!` list in `src-tauri/src/lib.rs`, the routes in `src/router.ts`, and the Status cells in `1.3.md` (take `main`'s file and re-add this batch's marks). Merge order still follows the table.

Why this order:

- **R01 first:** the security-descriptor module (F-002, F-004, F-008), the name rules (F-001), the hash function (F-006) and the access time on scan nodes (F-007) are shared. Building them once, with tests, keeps the feature batches small and stops two batches from writing the same module.
- **Readiness (R02, R03) next:** it is the highest-value new screen and F-004 and F-012 build on its report kind.
- **R04 (delta sync) is independent of the readiness work:** it only touches `transfer-core` and the Record screens. It waits for R01 only because R01 moves the name rules out of `transfer-core/src/prepare.rs`, which R04 also edits.
- **Storage (R06, R07)** touches only `cleanup-core`, `src-tauri/src/cleanup.rs` and the Cleanup screen, so it runs next to the migration batches.
- **R08 (remote shares) runs alone** because it touches every screen's path field and the delete pipeline.
- **R09** splits: F-011 (branding) touches only `report-core/src/doc.rs`, `page.css` and Settings, so it can go early; F-012 (runbook) needs the readiness, record and compare kinds to be final. The prompt does F-011 first and stops before F-012 if R03, R04 or R05 is not merged.

## Running the batches

Use the audit's orchestrator pattern (`docs/review/12-ORCHESTRATOR-PROMPT.md`) with this plan in place of the audit's: start one session per batch with the text inside its prompt's code block, add "Orchestrated by a parent session; report your PR number when it is open." on top, watch the PR, hand the merge to the owner, then start the next batch whose "needs" are merged. Cloud for R01 to R09 (local `cargo test` binaries are blocked by Defender ASR on the owner's machine); local for R10. Before asking the owner to merge the first 1.3 PR, check `gh release view v1.2.0`.

## R01: Shared plumbing

**Goal:** the shared modules the feature batches need, with tests. No user-visible change.

**Files:** see the table. `scan-core/Cargo.toml` gains `blake3` (already in the lockfile, D-13) and the `windows-sys` features `Win32_Security_Authorization` and `Win32_System_RestartManager` (D-24).

**Steps**

1. **Names.** Move `LONG_PATH_LIMIT`, `RESERVED_NAMES` and `is_valid_windows_name` from `transfer-core/src/prepare.rs` to `scan-core/src/names.rs`, keep `pub use` re-exports in `prepare.rs` so callers do not change, and add `NameIssue` checks returning every problem with a name (not just valid/invalid): reserved, trailing space, trailing dot, invalid character, control character, and the SharePoint profile list. Record's existing tests must pass unchanged.
2. **Hash.** Move `hash_file` to `scan-core/src/hash.rs` and re-export it from `transfer-core::copy`. Add `hash_head_tail(path, 64 KiB)` for the duplicate finder.
3. **Security.** `scan-core/src/security.rs`: `read(path, what) -> Result<Descriptor>` (owner SID, protected flag, decoded ACEs: SID, allow/deny, mask, inherited, applies-to flags, SDDL string); `SidNames` cache with `lookup(sid, server: Option<&str>)` that returns name, domain or "not found"; `well_known` risky principals and `is_wide_write(mask)` (D-06). Pure decoding and classification take bytes or structs and are tested on every platform; the Windows calls are `#[cfg(windows)]` with a stub that returns "not supported" elsewhere. The path is opened as a link itself (never follows a reparse point).
4. **In use.** `scan-core/src/inuse.rs`: `probe(path) -> InUse::{Free, InUse, Unreadable(code)}` and `holders(paths, cap, deadline)` through Restart Manager. Same Windows/stub split.
5. **Access time.** `Node.accessed_ms: Option<u64>` set from the same metadata the scan already reads. Check `scan-core/tests/perf.rs` still passes and say in the PR how the node size changed.

**Acceptance**

- `corepack pnpm check` green on CI, Windows job included.
- Unit tests for every name rule, ACE decoding from fixed masks, risky-principal classification, and SID-cache hits.
- Windows CI tests: read the descriptor of a temp folder the test created (owner is the current user), detect a file the test holds open with no sharing.
- `git grep -n "fn is_valid_windows_name"` shows only `scan-core`.

**Rollback:** revert. Nothing saved changes; `accessed_ms` is in memory only.

## R02: Migration readiness I (F-001, F-003)

**Goal:** the readiness screen, its saved report kind and export, with the name, long-path and in-use checks.

**Steps**

1. **F-001** Create `crates/migrate-core` (Apache-2.0, depends on `scan-core`, `serde`). `readiness::run(root, options, state) -> ReadinessReport`: scan with `scan_core::scan` (the walker already skips links and marks online-only and lossy names), then a name pass over the tree. `ReadinessReport` and every nested type are `#[serde(rename_all = "camelCase", default)]`.
2. **F-001** `report-core`: `Body::Readiness`, `ReportKind::Readiness`, `kinds/readiness.rs` (Reports-page row, HTML sections grouped by problem type, CSV). Save through `report_core::save` so the job fields come along.
3. **F-001** Tauri: `src-tauri/src/readiness.rs` with `readiness_start`, `readiness_cancel`, `readiness_children`, progress events; take the scan guard like Compare and Cleanup scans so it cannot overlap an elevated record. UI: `ReadinessPage.vue` (folder, destination root, target profile, Start, progress, grouped results one level at a time), route, Home tile, Compare link, Reports page label.
4. **F-003** In-use pass in `readiness::run` behind `options.check_in_use` (default true), using `scan_core::inuse`; skip online-only and link nodes. UI section and report section.

**Acceptance:** F-001 and F-003 criteria in `1.3.md`. Manual check (owner, Windows): run readiness on a folder with a long path, a `CON.txt` made with `\\?\`, and an open PST or a file held by `Start-Process powershell -ArgumentList '-c', '$f=[IO.File]::Open(...,"Open","Read","None"); sleep 600'`.

**Rollback:** revert. Saved readiness reports stay on disk; the reverted Reports page skips the unknown kind (check how `list` treats it and say so in the PR).

## R06: Storage I (F-006, F-007)

**Steps**

1. **F-006** `cleanup-core/src/dupes.rs`: candidates from the scan tree (files, not links, not online-only, not `hard_linked` second names, size ≥ minimum), group by size, then `hash_head_tail`, then `hash_file`; background job with progress and cancel; groups in managed state.
2. **F-006** Delete path: `cleanup_delete_duplicates(group ids, keep ids)` re-checks in Rust that each group keeps at least one file, re-hashes the kept file, re-checks size and time of the others, then calls `bulk::run` (Recycle Bin by default, log lines). `DuplicatesPanel.vue` with the "select all but the oldest" button and the existing bulk delete dialog.
3. **F-007** `cleanup-core/src/stale.rs`: per first-level folder totals for a threshold and `now`, with the optional access filter and the last-access-disabled hint (read `NtfsDisableLastAccessUpdate` on Windows). `StalePanel.vue`; selected rows go to the existing bulk delete dialog.
4. **F-006, F-007** Usage report fields (duplicate totals, stale threshold and per-folder totals), `#[serde(default)]`, HTML sections.

**Acceptance:** F-006 and F-007 criteria in `1.3.md`.
