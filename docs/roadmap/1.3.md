# Deep Server Analyzer 1.3 roadmap

Features the owner chose on 2026-10-24, planned on 2026-10-23 from `main` at `ddf7cb5` (1.2.0, audit complete). This file is the feature register, like `docs/review/02-FINDINGS-REGISTER.md` was for the audit. The batch order, file lists and session prompts are in [`1.3-plan.md`](1.3-plan.md) and [`prompts/`](prompts/).

## Merge hold

**No 1.3 feature PR merges before the owner has tagged v1.2.0.** `scripts\Set-ReleaseTag.ps1` tags `origin/main`, so anything merged first would ship inside 1.2.0. Batch sessions may branch, push and open PRs at any time; they stay unmerged until the tag `v1.2.0` exists on GitHub (`gh release view v1.2.0`). The orchestrator checks this before it asks the owner to merge the first 1.3 PR.

## Goals

1. **Before a migration:** one "Migration readiness" report on a source folder that lists everything that will break the copy or the target: bad names, long paths, risky or broken permissions, files in use.
2. **After the copy:** prove that permissions and owners arrived, not just bytes.
3. **At cutover:** re-run a Record that copies only what changed since the last run, without deleting anything at the destination.
4. **Storage work:** find duplicates, stale data and who owns the space, and see how a folder grows over time.
5. **Reach:** do all of this on `\\server\share` and admin shares, with saved server profiles and no stored passwords.
6. **Hand-over:** branded reports, and one runbook report for a whole migration job.

Non-goals (owner, 2026-10-24): CLI mode, scheduled runs, notifications, a verify-only mode, tamper-evident or PDF export, Excel export, multi-server inventory, mirror deletes.

## Rules that carry over from the audit

Every 1.3 batch keeps the safety rules in `CLAUDE.md`. The ones these features lean on most:

- Saved formats change additively only: every new field gets `#[serde(default)]`; nothing saved is renamed or removed. New report kinds are new `Body` variants.
- Every delete goes through `cleanup_core::bulk::run` and gets a `deletions.jsonl` line (F-006, F-007).
- Folder walks never follow reparse points; link checks use `cleanup_core::pathsafe` or the scan tree's `Kind::Link`.
- OneDrive online-only files are never opened, read or hashed, in any feature (F-003, F-006, F-008 read metadata only).
- Long jobs are `async` + `spawn_blocking`, stream progress about every 100 ms, and keep big results in managed state.
- Every colour is an `--app-*` token in `src/styles.css`.
- Webview commands take ids, not raw paths, except where a path is the input (a folder to scan); those are canonicalized once in Rust (`scan_core::paths::canonical_root`).
- Apache-2.0 only. Never copy source from GPL tools (WinDirStat, and the GPL parts of other disk tools). Windows API docs and MIT/Apache crates are fine.

### F-001: Long paths and bad names

**Problem.** A migration fails late, file by file, on names the target cannot hold: paths over 260 characters, names with trailing spaces or dots, reserved device names (`CON`, `NUL`, `COM1`...), invalid characters, and names OneDrive or SharePoint reject. Record's pre-flight already finds some of these (`transfer_core::prepare`), but only as part of starting a copy, and only for a Windows target.

**User-facing behaviour.**

- A new **Migration readiness** screen (`/compare/readiness`, linked from Home and the Compare page) takes a source folder, an optional planned destination root, and a target profile: **File server (NTFS)** (default) or **OneDrive / SharePoint**.
- It scans the source once and lists every name problem with the path, the rule it breaks, and a fix hint ("rename to ...", "shorten by 34 characters").
- Long paths are measured as they will be at the destination when a destination root is given (`D:\Shares\Finance` + relative path), otherwise as they are at the source.
- Results group by problem type with counts, and open one folder level at a time like the other screens.
- The report is saved as a new **Readiness** report kind and exports to HTML and CSV from the Reports page.

**Crates/files.** `scan-core` (new `names.rs`: the name rules move here from `transfer-core/src/prepare.rs`, which then calls them), new crate `migrate-core` (`readiness.rs`), `report-core` (`kinds/readiness.rs`, `Body::Readiness`, `ReportKind::Readiness`), `src-tauri/src/readiness.rs` (new commands), `src/pages/ReadinessPage.vue`, `src/lib/readiness.ts`, `src/router.ts`, `src/pages/HomePage.vue`, `src/pages/ComparePage.vue` (link only).

**Risks.** Moving the name rules must not change Record's pre-flight (its tests must pass unchanged). SharePoint rules change over time; keep them in one table with a comment naming the Microsoft doc and its date. A name that is not valid Unicode (`Node::lossy_name`) must be reported, not built into a path.

**Acceptance criteria.**

- Each rule has a unit test with a passing and a failing name: reserved names with and without extension, trailing space, trailing dot, each invalid character, control characters, the SharePoint list (`.lock`, `_vti_`, `desktop.ini`, `~$` prefix warning, 400-character path limit), and an unpaired surrogate.
- With a destination root given, a path that is 250 characters at the source and 270 at the destination is reported; without one it is not.
- Record's existing `prepare` tests pass unchanged after the move.
- A readiness report saved by this version loads in the Reports page, and a 1.2.0 reports folder still lists and opens.
- Links and junctions are listed as "not followed" and never entered; online-only files are checked by name only.

### F-002: NTFS permissions audit

**Problem.** Before moving a share the technician needs to know what the permissions look like: folders that break inheritance, access granted to accounts that no longer exist, and folders anyone can write to. Today that means `icacls` output and a spreadsheet.

**User-facing behaviour.**

- The readiness screen gets a **Permissions** section (on by default).
- For every folder, and every file that has its own (non-inherited) entries, it reads the owner and the DACL and reports:
  - **Inheritance broken:** the folder's DACL is protected (it does not inherit from its parent).
  - **Unknown accounts:** entries or owners whose SID no longer resolves (shown as `S-1-5-21-...`).
  - **Wide write access:** Everyone, Authenticated Users, BUILTIN\Users, Domain Users or Anonymous with write, modify or full control.
  - **Explicit file entries:** files with their own entries (counted, listed under their folder).
  - **Unreadable:** folders whose permissions could not be read (with the Windows reason).
- **Export permissions (CSV)** writes one row per access entry: path, owner, inheritance protected, account name, SID, allow/deny, rights in words, raw mask (hex), inherited, applies to; folder rows also carry the SDDL string.
- An option **Check every file** (off by default) reads every file's permissions instead of folders only.

**Crates/files.** `scan-core` (`security.rs` from R01), `migrate-core` (`acl_audit.rs`), `report-core` (`kinds/readiness.rs` permissions section, permissions CSV layout), `src-tauri/src/readiness.rs`, `src/pages/ReadinessPage.vue`, `src/components/PermissionsPanel.vue`.

**Risks.** Reading security on millions of files is slow: folders-only is the default for that reason, and lookups are cached per SID. SID lookups for a UNC path must ask the server (`LookupAccountSidW` with the server name), not the local machine, or every domain-local group looks orphaned. Elevated runs read more (backup privilege); the report says whether it ran elevated. The audit only reads; it never changes a descriptor.

**Acceptance criteria.**

- Unit tests (Windows CI) on a temp tree: a folder with protected DACL, an ACE for a deleted local user's SID (create user, grant, delete user, or use a made-up `S-1-5-21-1-2-3-1001`), an Everyone:Modify grant, a file with an explicit ACE, and a folder the test denies itself `READ_CONTROL` on.
- Each risky principal and each rights level (read only is not flagged; write, modify, full control are) has a decode test on raw masks that runs on every platform.
- The CSV has one row per ACE and survives a CSV round trip (commas, quotes, non-ASCII names).
- Links are not entered; the walk uses the scan tree, so a junction to `C:\Windows` adds no rows.

### F-003: Open and locked files

**Problem.** A copy silently skips or fails on files that are open with an exclusive lock: PST files, databases, VM disks, files open in Office. The technician finds out from the Record report after the copy.

**User-facing behaviour.**

- The readiness screen gets an **In use** section (on by default, can be turned off for speed).
- Each file is opened for read with full sharing; a sharing or lock violation marks it **In use**.
- For in-use files on a local drive, the Restart Manager names the program that holds it (`OUTLOOK.EXE (PID 4120)`) for up to the first 500 such files; on a share the holder shows as "on the server (program unknown)".
- The section explains that this is a moment in time and suggests closing the program or copying in Watch mode with the other tool.

**Crates/files.** `scan-core` (`inuse.rs` from R01: the open probe and Restart Manager calls behind `#[cfg(windows)]`, a stub elsewhere), `migrate-core` (`readiness.rs` in-use pass), `report-core` (`kinds/readiness.rs`), `src-tauri/src/readiness.rs`, `src/pages/ReadinessPage.vue`. R01 adds the `windows-sys` feature `Win32_System_RestartManager` to `scan-core`.

**Risks.** The probe opens every file, which is slow on big shares; it runs in parallel with progress and can be cancelled. It must never open an online-only file (that would download it) or a link. Opening must not change the last-access time the stale report relies on: open with `FILE_FLAG_BACKUP_SEMANTICS` off and close at once; note that NTFS may still update access time and say so in the report. The Restart Manager session is per call, freed on every path, and capped (500 files, 30 s).

**Acceptance criteria.**

- Windows CI test: a temp file opened by the test with `share_mode(0)` is reported as in use, and the holder is the test process; a normal file is not.
- Online-only placeholders and links are skipped (test with the tree flags, no real OneDrive needed).
- Cancelling stops the pass within one progress tick.
- Non-Windows builds compile and report "not checked on this system".

### F-004: Permissions compare after the copy

**Problem.** Compare proves sizes match. After a migration the client also asks "did the permissions come across?" Robocopy `/COPY:DATSOU` and similar tools can drop owners or ACEs without failing the copy.

**User-facing behaviour.**

- Compare gets a **Compare permissions** option (off by default; on by default when a Record run with "copy permissions" is selected as the source of the compare).
- For each folder pair (and each file pair where either side has explicit entries) it compares owner, inheritance protection and explicit entries:
  - **Same**, **Owner differs**, **Entries differ** (with the added and missing entries), **Inheritance differs**, **Not readable**.
  - **Same name, different account:** the entries name the same account but the SIDs differ (a local account recreated on the new server). Shown in amber, not red.
- Inherited entries are compared only at the compare root, because below it they follow from the root.
- The saved compare report gains a permissions section (additive fields), and the export gets a permissions CSV.

**Crates/files.** `scan-core` (`security.rs`), `migrate-core` (`acl_diff.rs`), `report-core` (`kinds/compare.rs`, new `#[serde(default)]` fields), `src-tauri/src/compare.rs`, `src/pages/ComparePage.vue`, `src/components/CompareTable.vue` (a permissions status column), `src/lib/compare.ts`.

**Risks.** Comparing raw SIDs flags every domain migration; comparing names hides a wrong account. Showing both statuses (decision D-09) handles that. Compare's existing size results and report must not change when the option is off.

**Acceptance criteria.**

- Pure tests on decoded ACLs: equal, owner differs, an ACE missing on the right, an extra deny ACE, a different mask, protected on one side only, same name with different SID.
- Windows CI test on two temp trees where one folder's ACL is changed after copying.
- With the option off, compare output and saved JSON are byte-identical to 1.2.0 for the same tree (fixture test).

### F-005: Delta sync (re-run a Record)

**Problem.** A migration copies the bulk days ahead, then needs a short final pass at cutover with only what changed. Today the technician starts a new Record and every file is compared again with no link to the first run.

**User-facing behaviour.**

- A finished Record run (Completed or Cancelled) gets **Copy changes since this run**.
- It starts a new run with the same source, destination and settings, linked to the previous one (shown as "Changes since run of 21 Oct, 18:02").
- A file is copied when it is missing at the destination, its size differs, or its modified time differs beyond the 2 s tolerance; files the previous run listed as not copied are tried again.
- A file changed at the destination after the previous run finished (destination newer than both the source and that finish time) is **not** overwritten; it is listed as "Changed at the destination since the last run".
- Nothing is ever deleted at the destination. Files that exist only at the destination are counted ("12 files only at the destination, left in place").
- The report header shows the chain: this run, the run it follows, and totals for "changed", "new", "retried", "unchanged".

**Crates/files.** `transfer-core` (`lib.rs`: `RunSummary.previous_run_id` and `delta` totals, `#[serde(default)]`; `prepare.rs`: delta planning; `run.rs`), `report-core` (`kinds/record.rs`), `src-tauri/src/record.rs` (new `record_delta` command), `src/pages/RecordReportPage.vue`, `src/pages/RecordPage.vue`, `src/lib/record.ts`.

**Risks.** Overwriting a destination file someone edited after cutover started; the "changed at the destination" rule prevents that. Clock skew between servers: the 2 s tolerance stays; times are compared as UTC. Watch-mode runs cannot be re-run as a delta (another tool copies); the button is hidden for them.

**Acceptance criteria.**

- Tests on temp trees: unchanged file is skipped; changed size, changed time (newer and older), new file, and previously failed file are copied; a destination-newer file is left and listed; a destination-only file is left and counted.
- Old run folders without the new fields load and show no chain.
- Cancelling a delta run leaves the previous run untouched.
- No code path in the batch calls any delete function on the destination (grep check in the PR).

### F-006: Duplicate finder

**Problem.** File servers fill with copies of the same installers, ISOs, exports and photo dumps. Disk Cleanup shows big folders but not repeated content.

**User-facing behaviour.**

- After a Disk Cleanup scan, a **Duplicates** panel finds files with identical content: same size first, then the first and last 64 KiB, then a full BLAKE3 hash.
- Groups list the files, their folders and dates, sorted by space that could be freed.
- Minimum size 1 MiB by default (choices 64 KiB, 1 MiB, 10 MiB, 100 MiB).
- Nothing is selected automatically. **Select all but the oldest in each group** is a button the user presses.
- Delete goes through the existing bulk delete dialog: Recycle Bin by default, `deletions.jsonl` lines, protected-path checks. Rust refuses a delete that would remove every copy in a group, and re-hashes the kept copy just before deleting the others.

**Crates/files.** `scan-core` (`hash.rs`: `hash_file` moves here from `transfer-core/src/copy.rs`, which re-exports it), `cleanup-core` (new `dupes.rs`), `src-tauri/src/cleanup.rs`, `src/components/DuplicatesPanel.vue`, `src/pages/CleanupPage.vue`, `src/lib/cleanup.ts`, `report-core` (`kinds/usage.rs`: duplicate totals, additive).

**Risks.** Hashing reads every candidate byte; it runs in the background with progress and cancel. Hard links to the same file are not duplicates (same file id; the scan already marks `hard_linked`). Online-only files are never hashed. A file that changes between hash and delete: the kept copy is re-hashed and the others are re-checked by size and time before deletion.

**Acceptance criteria.**

- Tests: equal content in three files makes one group; same size with different content makes none; equal first and last 64 KiB with a different middle makes none; hard links make none; online-only and link nodes are skipped.
- Deleting all files of a group is refused in Rust with a clear message, even when the webview sends every id.
- Every deleted duplicate has a `deletions.jsonl` line (test reads the log).

### F-007: Stale data report

**Problem.** Clients ask "how much of this share has nobody touched in years?" before buying storage or archiving.

**User-facing behaviour.**

- A **Stale data** panel after a Disk Cleanup scan: files not modified in N years (default 3; choices 1, 2, 3, 5, 7, 10).
- Grouped by first-level folder under the scan root: stale bytes, stale files, share of the folder, newest change in the group.
- An option **Also not opened** adds the last-access time, with a note when Windows is not keeping last-access times (`NtfsDisableLastAccessUpdate`).
- Rows can be selected and deleted through the bulk delete dialog, like any other row.
- The saved usage report keeps the threshold and the per-folder totals; the HTML export has a stale section.

**Crates/files.** `scan-core` (`scan.rs`: `Node.accessed_ms`, from R01), `cleanup-core` (new `stale.rs`), `src-tauri/src/cleanup.rs`, `src/components/StalePanel.vue`, `src/pages/CleanupPage.vue`, `src/lib/cleanup.ts`, `report-core` (`kinds/usage.rs`).

**Risks.** Last-access time is unreliable; it is never the default rule. Files with a modified time in the future or before 1980 are counted as "date unknown", not stale.

**Acceptance criteria.**

- Tests with fixed `now`: thresholds at the boundary (exactly 3 years is stale), future and missing dates, access-time filter on and off, grouping by first-level folder.
- Old usage reports without stale fields load and export.

### F-008: Space by owner

**Problem.** "Who is using all the space?" needs per-user totals, not folder totals.

**User-facing behaviour.**

- A **By owner** button after a Disk Cleanup scan reads each file's owner and shows a table: account, files, space, share of the scan, top three folders.
- Unknown SIDs show as the SID with "(account not found)"; files whose owner could not be read show as "Unknown (no access)".
- Clicking an owner filters the folder view to that owner's files.
- The saved usage report keeps the owner table (additive).

**Crates/files.** `scan-core` (`security.rs` owner read and SID cache), `cleanup-core` (new `owners.rs`), `src-tauri/src/cleanup.rs`, `src/components/OwnersPanel.vue`, `src/pages/CleanupPage.vue`, `src/lib/cleanup.ts`, `report-core` (`kinds/usage.rs`).

**Risks.** One security read per file: on demand only, parallel, cancellable, with progress. Results live in managed state keyed by the scan, and are dropped when a new scan starts. Reading the owner does not open file data, so online-only files are included (their owner is metadata) but count 0 bytes on disk, as in the scan.

**Acceptance criteria.**

- Aggregation tests on a fake tree with injected owners: totals, top folders, unknown and unreadable buckets.
- Windows CI test: files created by the test are owned by the test user's SID.
- A new scan clears the previous owner table.

### F-009: Scan history, growth and forecast

**Problem.** A single scan shows where the space is now, not what is growing or when the disk will be full.

**User-facing behaviour.**

- Every completed Disk Cleanup scan saves a small snapshot: drive used and free space, root totals, and folders down to three levels that hold at least 0.5% of the root (at most 2,000 folders).
- The Disk Cleanup screen gets **What grew**: pick an earlier snapshot of the same folder (default: the previous one) and see folders by growth in bytes and percent, plus new and removed folders.
- A **Forecast** line: "At the last 90 days' rate, this drive is full in about 140 days." It shows only with at least 3 snapshots spread over at least 14 days and a positive trend under 5 years; otherwise "Not enough history yet" or "Not growing".
- Settings gets **Keep scan history** (on by default) and a "Delete history" button for one folder or all.

**Crates/files.** `report-core` (new `snapshots.rs`: store, retention, growth diff, forecast), `src-tauri/src/cleanup.rs` (save after scan, `cleanup_history`, `cleanup_growth`), `src/components/GrowthPanel.vue`, `src/pages/CleanupPage.vue`, `src/pages/SettingsPage.vue`, `src/lib/cleanup.ts`.

**Risks.** Disk growth over months: snapshots are small (capped folders) and pruned (decision D-14). The store lives under the reports folder, which is already on the never-delete list, in a subfolder that `report_core::prune` does not touch (it only removes top-level `*.json`); a test pins that. Forecasts mislead when a big one-off copy happened; the text says "at this rate" and shows the fit window.

**Acceptance criteria.**

- Tests: snapshot write is atomic and a torn file is skipped; retention keeps the newest 60 per root and drops anything older than 2 years; `prune` leaves the snapshots folder alone.
- Growth diff on two synthetic snapshots: grown, shrunk, new, removed.
- Forecast: fewer than 3 points or under 14 days gives "not enough history"; flat or shrinking gives "not growing"; a linear series gives the expected day count within one day.

### F-010: Remote shares and saved server profiles

**Problem.** Most of this work is on file servers. Paths like `\\fs01\Finance` and `\\fs01\D$` work in some screens and not others, and the technician retypes them every time.

**User-facing behaviour.**

- Compare, Record, Readiness and Disk Cleanup accept `\\server\share` and admin shares (`\\server\C$`) everywhere a folder is picked.
- A **Servers** section in Settings saves profiles: display name, server name, optional user name, notes. **List shares** shows the server's shares (hidden `$` shares marked), and each one can be picked as a path.
- Access uses the current Windows sign-in. When it is denied, the existing sign-in dialog connects with a user name and password for this session only (not saved to the Windows profile). **Passwords are never stored** by the app, in any form.
- Disk Cleanup on a share is **scan and report only**: delete buttons are hidden and Rust refuses deletes on UNC paths, because network deletes skip the Recycle Bin.

**Crates/files.** `transfer-core` (`share.rs`: share listing with `NetShareEnum`, `windows-sys` feature `Win32_NetworkManagement_NetManagement`), `src-tauri/src/record.rs` (`share_connect` reused), new `src-tauri/src/servers.rs` (`servers_list_shares`), `src-tauri/src/cleanup.rs` (UNC delete refusal), `cleanup-core/src/bulk.rs` (refusal at the pipeline, so no command can bypass it), `src/components/PathField.vue`, `src/components/ShareSignIn.vue`, `src/pages/SettingsPage.vue`, `src/lib/servers.ts`.

**Risks.** Admin shares need admin rights on the server; errors map to the existing `connect_error_text` words. A profile store that grows a password field later would break the rule: the profile type has no secret field, and a test asserts the saved JSON never contains the key `password`. Readiness and owner lookups must resolve SIDs against the server (see F-002).

**Acceptance criteria.**

- `bulk::run` refuses any UNC target with a clear message (unit test with `\\server\share\x` and `\\?\UNC\server\share\x`).
- Profile save/load round trip in `src/lib/servers.test.ts`; the saved value has no password.
- `share_root` tests cover admin shares (`\\fs01\C$`).
- Windows CI test lists the shares of `\\localhost` (at least `C$` or `ADMIN$` when elevated; otherwise the call reports access denied cleanly).

### F-011: Branded reports

**Problem.** Reports go to clients. The company name already appears (`brand` in Settings), but there is no logo and the job details are easy to miss.

**User-facing behaviour.**

- Settings gets **Company logo**: pick a PNG or JPEG up to 256 KB; preview; remove.
- Every HTML report shows the logo and company name in the header, and a "Prepared for" block with client, ticket and technician from the job fields when they are set.
- CSV exports gain a short header block with the same job fields (additive rows before the table, behind an option **Include job details in CSV**, on by default).

**Crates/files.** `report-core` (`doc.rs`: header layout, logo as a `data:` image, which the report CSP already allows; new `branding.rs`: logo store), `src-tauri/src/reports.rs` (`branding_set_logo`, `branding_clear_logo`; export reads the logo itself), `src/pages/SettingsPage.vue`, `src/lib/job.ts`, `report-core/src/assets/page.css` (header layout; the CSP hash changes, update it and the explorer fixture).

**Risks.** A logo is a file from the user: Rust checks the PNG or JPEG signature and size and stores its own copy, so the webview never passes a path at export time. SVG is not accepted (it can carry script). Changing `page.css` changes its CSP hash; the fixture refresh must be reviewed.

**Acceptance criteria.**

- Tests: a PNG and a JPEG are accepted; an SVG, a renamed text file and a 300 KB file are refused.
- HTML export contains the logo `data:` URI and escaped job fields; without a logo the header is unchanged from 1.2.0 except for the "Prepared for" block.
- `UPDATE_FIXTURES=1 cargo test -p report-core explorer_fixture` diff is reviewed and committed.

### F-012: Migration runbook report

**Problem.** A migration has a before (readiness), a copy (Record, possibly several delta runs) and an after (compare, permissions compare). The client wants one document.

**User-facing behaviour.**

- On the Reports page, **New runbook** lets the user pick reports for one job: one readiness report, one or more Record runs, and compare reports. Reports with the same ticket number as the first pick are suggested first.
- The runbook is saved as its own report kind holding the job fields and the ids of its parts, in order.
- Its HTML export is one document: a summary page (job, dates, verdict per stage), then each part's section in order (before, copy, after), each with its own verdict tile. CSV export is one file with a section column.
- A part that was deleted later shows as "Report no longer available" in its place; the runbook still exports.

**Crates/files.** `report-core` (`kinds/runbook.rs`, `Body::Runbook`, `ReportKind::Runbook`, combined `Document` builder), `src-tauri/src/reports.rs` (`runbook_create`), `src/pages/ReportsPage.vue`, `src/components/RunbookDialog.vue`, `src/lib/reports.ts`.

**Risks.** A combined HTML document can get large; each part keeps its own `MAX_HTML_ROWS` cap. Ids are checked in Rust against the reports and records folders; the webview never passes paths.

**Acceptance criteria.**

- Tests: a runbook with a readiness, two record runs and a compare renders sections in order; a missing part renders the placeholder; CSV has the section column.
- Deleting a runbook does not delete its parts; deleting a part does not delete the runbook.
- Older app versions ignore the new kind: a 1.2.0 `list` would skip an unknown kind; check that `report_core::list` skips unknown kinds today, and if it does not, log a DSA-style note in the PR instead of changing old behaviour.

## Decisions

The owner asked for recommended answers. These are the defaults the batch prompts build in. Change a row here before the batch runs if the owner disagrees.

| #    | Question                                  | Decision                                                                                                                                                                                                                                                                    | Why                                                                                                                                                          |
| ---- | ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D-01 | Where does readiness live in the app?     | A new screen at `/compare/readiness`, linked from Home and Compare. No new nav rail item.                                                                                                                                                                                   | It is a migration step next to Compare and Record, which already live under `/compare`. Keeps the rail at five items.                                        |
| D-02 | Where do readiness and ACL logic live?    | A new workspace crate `migrate-core` that depends on `scan-core` only. `report-core` depends on it for the report kinds.                                                                                                                                                    | Keeps `transfer-core` about copying and keeps dependencies pointing down, as the audit set up.                                                               |
| D-03 | Long-path threshold                       | Over 259 characters (MAX_PATH minus the terminator, the existing `LONG_PATH_LIMIT`) for a file server; 400 for OneDrive/SharePoint. Measured at the destination when a destination root is given.                                                                           | Matches Record's pre-flight and the documented limits; the destination length is what actually fails.                                                        |
| D-04 | Default target profile                    | **File server (NTFS)**. OneDrive/SharePoint rules are a second profile the user picks.                                                                                                                                                                                      | Most jobs are server to server; SharePoint rules would flag names that are fine on NTFS.                                                                     |
| D-05 | Permissions audit scope                   | Folders always; files only when they have explicit entries. **Check every file** is an option, off by default.                                                                                                                                                              | Folder ACLs carry almost all real-world permission design; per-file reads multiply the time by the file count.                                               |
| D-06 | Which grants count as "wide write access" | Everyone, Authenticated Users, BUILTIN\Users, Domain Users (RID 513), Anonymous, with any of write data, append, delete, write DAC, write owner, generic write or generic all. Reported as warnings, not blockers.                                                          | These are the principals auditors ask about; read access for them is normal on shares. Warnings, because they do not stop a copy.                            |
| D-07 | Orphaned SID detection                    | `LookupAccountSidW` returns "none mapped", asked of the machine that holds the path (the server for UNC). Cached per SID per run.                                                                                                                                           | Asking the local machine would report every server-local group as orphaned.                                                                                  |
| D-08 | Locked-file detection                     | Open each file for read with full sharing; a sharing or lock violation means in use. Restart Manager names the holder for local paths only, first 500 files, 30 s cap. On by default, can be turned off.                                                                    | The open probe is what a copy will hit. Restart Manager cannot see processes on another server, and it is slow per call.                                     |
| D-09 | Permissions compare: SIDs or names        | Compare by SID. When the SIDs differ but resolve to the same account name, show "Same name, different account" in amber. Inherited entries are compared only at the root.                                                                                                   | SID is the truth for access; the amber status keeps domain-to-domain and local-account migrations readable without hiding a real mismatch.                   |
| D-10 | How delta sync detects change             | Missing at the destination, size differs, or modified time differs by more than 2 s (either direction); plus files the previous run did not copy. No hashing for detection. A destination file newer than both the source and the previous run's finish is left and listed. | Same cost as a normal Record pre-flight; catches files restored with older dates; never overwrites work done at the destination after cutover started.       |
| D-11 | Delta sync deletes                        | Never. Destination-only files are counted and left.                                                                                                                                                                                                                         | Owner: no mirror deletes.                                                                                                                                    |
| D-12 | Duplicate rules                           | Minimum 1 MiB; size, then first and last 64 KiB, then full BLAKE3. Hard links are not duplicates. No auto-select. Rust refuses to delete every copy of a group and re-hashes the kept copy first.                                                                           | Small files free little space and cost the most hashing. BLAKE3 is already used by Record. The Rust-side guard means a webview bug cannot delete all copies. |
| D-13 | Hashing code location                     | Move `hash_file` from `transfer-core` to `scan-core::hash` and re-export it; `scan-core` gains `blake3`, already in `Cargo.lock` at the same version.                                                                                                                       | `cleanup-core` may only depend on `scan-core`. No new crate enters the lockfile, so this is not a new dependency; R01 states it in its PR.                   |
| D-14 | Stale threshold                           | Not modified in **3 years** by default; choices 1, 2, 3, 5, 7, 10. Last-access time is an optional extra filter, never the default.                                                                                                                                         | Three years is the common archive policy line. Access time is often not maintained on servers.                                                               |
| D-15 | Owner pass                                | On demand after a scan, not part of every scan. Results dropped on the next scan.                                                                                                                                                                                           | One security read per file is too slow to add to every scan.                                                                                                 |
| D-16 | Snapshot storage and retention            | `Reports\snapshots\<key>\<timestamp>.json`, where key is the hex SHA-256 of the canonical root. Newest 60 per root, nothing older than 2 years. Folders to depth 3 and at least 0.5% of the root, capped at 2,000. History on by default.                                   | The reports folder is already protected and its prune ignores subfolders, so no new data folder or env override is needed. The caps keep each file small.    |
| D-17 | Forecast method                           | Least-squares line over drive used bytes from the last 90 days of snapshots. Needs 3 points over 14 days and a positive slope; hidden above 5 years.                                                                                                                        | Simple, explainable in one sentence, and honest about when there is not enough data.                                                                         |
| D-18 | Remote credentials                        | Never store passwords. Use the current Windows session; on access denied, the existing one-time sign-in (`WNetAddConnection2W`, not saved to the profile). The user can also run `net use` themselves. Profiles hold no secret field.                                       | Owner rule. Windows already manages the session; storing secrets would need DPAPI, key handling and a new attack surface.                                    |
| D-19 | Where server profiles are stored          | In the webview's `localStorage` (`analyzer-servers`), like recent paths.                                                                                                                                                                                                    | They are UI convenience with no secrets; no new saved Rust format to keep compatible.                                                                        |
| D-20 | Disk Cleanup deletes on shares            | Refused in 1.3 (in `bulk::run`). Scan, duplicates, stale and owners work read-only on shares.                                                                                                                                                                               | The Recycle Bin does not cover network paths, so every delete would be permanent without the admin confirm flow.                                             |
| D-21 | Where branding is stored                  | Company name stays in `localStorage` (`analyzer-brand`, today's setting). The logo is copied by Rust to `Reports\branding\logo.png` or `.jpg`; exports read it from there.                                                                                                  | The reports folder is protected; the webview never hands a path to export; the name setting does not move, so 1.2.0 users keep it.                           |
| D-22 | Logo formats                              | PNG or JPEG, at most 256 KB, checked by signature in Rust. No SVG.                                                                                                                                                                                                          | SVG can carry script; the size cap keeps every exported report small.                                                                                        |
| D-23 | How a runbook is built                    | The user picks parts on the Reports page; same-ticket reports are suggested. Saved as a `Runbook` kind holding ids, rendered from the parts at export time.                                                                                                                 | No hidden "job" object to keep in sync; parts stay independent reports; the ticket field already exists in every report.                                     |
| D-24 | `windows-sys` features                    | Allowed: `Win32_Security_Authorization` and `Win32_System_RestartManager` in `scan-core`, `Win32_NetworkManagement_NetManagement` in `transfer-core`. Same crate and version.                                                                                               | Features of a crate already in the lockfile, not new dependencies. Each batch lists the feature it adds in its PR.                                           |
